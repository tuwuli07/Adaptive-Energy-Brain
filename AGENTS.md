# Project Development Instructions

These instructions apply to both GitHub Copilot and Codex. Keep changes scoped
to the requested phase and follow the contracts below.

## Architecture and existing interfaces

- `src/data/` owns acquisition, validation, chronological splitting, scaling,
  graph construction, and forecasting sequences. See
  [data requirements](docs/data_requirements.md) and
  [Part 2 completion](docs/part2_completion_report.md).
- `src/simulation/` is the existing physical simulator. Reuse
  `MicrogridEnvironment`, `AgentObservation`, `ForecastFeature`,
  `BatteryAction`, `DispatchResult`, and the existing metrics; do not replace
  or duplicate the simulator. See
  [simulation architecture](docs/simulation_architecture.md) and
  [Part 3 completion](docs/part3_completion_report.md).
- `src/baselines/` and `src/evaluation/` implement the shared
  `BaselineController.reset()` / `select_action(observation) -> BatteryAction`
  contract, four rule-based baselines, and their comparison workflow. Preserve
  their behavior. See [baseline architecture](docs/baseline_architecture.md)
  and [Part 4 completion](docs/part4_completion_report.md).
- `src/forecasting/` is the designated home for Part 5 forecasting. The
  GNN-Transformer model is in `src/forecasting/models/`; the Part 5.8
  train/validation loop must use its masked target contract and must not read
  or use the held-out test partition for selection.

## Coding conventions

- Follow the existing Python package layout, naming, configuration, and error
  handling patterns. Keep configuration in versioned YAML unless a
  machine-readable artifact contract clearly benefits from JSON.
- Keep data preparation, forecasting, control, and physical simulation
  responsibilities separate. Reuse existing utilities and interfaces instead
  of introducing parallel implementations.
- Do not add a dependency or service unless the current task requires it;
  optional technologies must remain optional.
- Record assumptions explicitly. Never present synthetic or hypothetical
  values as measured campus data.

## Dataset and experiment reproducibility

- Preserve raw inputs. Record source, license, origin, units, time zone,
  coverage, transformations, seed, and checksums for datasets and derived
  artifacts.
- Keep runs reproducible: record configuration, seed, data/split hashes,
  model/training settings, software versions, and artifact hashes using
  [the experiment metadata schema](configs/experiment_metadata.schema.json).
- Use training data for fitting, validation for model selection, and the
  held-out test partition only for final evaluation. Freeze choices before
  test evaluation and do not overwrite existing datasets or experiment
  artifacts.
- On Windows, use the existing project `.venv` when available and keep
  machine-specific external-storage paths in the ignored `.env.storage`
  generated by [the Windows storage setup](docs/windows_storage_setup.md).
  Prefer the external drive selected by `scripts/setup_windows_storage.ps1`
  for caches and new experiment outputs; do not move or delete existing data,
  checkpoints, or environments without explicit approval. Keep shared config
  paths relative and preserve Colab's independent Drive paths.

## Future-data leakage

- Forecast inputs must be available at their issue time. Preserve forecast
  issue time, data cutoff, and target timestamps; future realized observations
  belong only in labels/evaluation, never in model inputs.
- Fit preprocessing on training data only. Do not fit or tune on validation or
  test data, create windows across split boundaries, or use test results for
  model selection.
- Preserve the causal `AgentObservation` boundary. A controller must not
  access future replay rows, simulator internals, or realized current-step
  outcomes.

## Testing and scope

- Run the smallest relevant tests, then the full suite when shared interfaces
  or behavior may be affected. From the project root:
  `.\.venv\Scripts\python.exe -m pytest tests -q -p no:cacheprovider`
- Do not change the existing physical simulator or completed rule-based
  baselines as part of forecasting work. Do not rewrite working components to
  adopt a new framework. Make the smallest compatible change and add tests for
  altered or new behavior.
- Do not implement the RAG assistant during Part 5 or add LLM calls to model
  training. Do not add, expose, or commit API keys.

## Development handoff

Update [the development handoff](docs/development_handoff.md) at phase/task
boundaries. Record the current phase and task, completed work, exact verified
test command and result, known issues, and the next bounded task. Do not claim
tests, data, or model results that were not verified.
